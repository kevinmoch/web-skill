## 何时使用

用户要一份**文档**时使用——不管他叫它「文档」「word」「office 文档」「报告」
「说明」，还是「通报」「公文」「通告」。出现下面任何一条，就**必须**用本技能：

- 用户限定了数据范围：「当前页面的数据」「只要这一类」「别的不用管」；
- 用户指定了内容或结构：写哪几段、放哪张图、发给谁看；
- 用户看完后提出任何修改要求；
- 用户要把**刚才对话里已经输出过的**图表 / 表格 / 卡片汇总成一份文档。

只有当用户**笼统地**要一份标准件、既没限定范围也没提内容要求时，
技能库里若有固定模板的同类技能，那类更快更稳，可以优先用；但它一个字都改不了，
用户随后提出任何修改，都要回到本技能重做一版。

## 先决定这是哪一种文档

`doc.docType` 只有两个取值，**默认 `"plain"`**：

| 用户的说法                                                             | docType      | 长什么样                                                                                   |
| ---------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------ |
| 文档、office 文档、word 文档、报告、说明、纪要、方案、总结（**默认**） | `"plain"`    | 普通 Word 文档：居中大标题、可选副标题与元信息、正文分节。没有红头、没有文号、没有落款盖章 |
| 通报、公文、通告、红头文件、发文                                       | `"official"` | 红头公文：发文单位红字 + 红线、文号、公文标题、主送单位、末尾落款                          |

**拿不准就用 `"plain"`。** 用户说「生成一份文档」却收到一份红头通报，
比收到一份朴素的 Word 文档要糟得多。`"official"` 需要发文单位，
没有就问用户，不要编。

## 步骤

1. 先用 `read_skill_file` 读本技能的 `references/authoring.md`。那是文档数据契约：
   `doc` 对象的每个字段、11 种块的写法、什么时候用哪种块。**不要跳过**——
   凭印象拼出的 `doc` 会被 `publish` 逐条挡回来，白跑一轮。
2. 收集数据。**取哪些数据由你判断，但以用户说的为准**：

   - 用户说了范围（「当前页面的」「只要这一类」「这段时间的」），就按他说的取。
     顺手多拉进来的那部分，在用户眼里就是你没听懂他的话；
   - 用户没说范围，就由你决定取哪些：该跨页面、跨工具汇总的就去汇总，
     不要因为保守而少取——文档缺了关键一块同样算失败；
   - 你判断补一点范围外的数据会让这份文档更站得住时可以补，但要么先问用户一句，
     要么在文档里标明它是额外补充的。

   本技能**不带取数脚本**——取数手段随宿主而异，用你当前会话里能用的一切：
   页面感知工具读当前页面、导航或切标签页到别的页面再读、宿主挂上来的 MCP 工具、
   数据源工具、别的技能刚产出的结果，或者直接问用户。要跨多个页面汇总时**一页一页来**：
   进一页、读完、把要用的数字记下来，再进下一页。
   **每个数字都必须来自你真正读到的内容**：文档发出去就是凭据，读不到就写「暂缺」
   或直接告诉用户读不到，绝不估算、推测或编造任何数字、名称与日期。
   同时记下数据出处（页面名 / 工具名 / 数据源 id），`publish` 的 `dataSource` 要如实填。

3. 发文单位、抄送范围、统计口径、时间范围这类数据里没有的信息，先问用户一句，
   **不要编造**机构名或文号。用户说「随便」就用中性写法，或干脆省掉该字段。
4. 拼出 `doc` 对象，调用 `authored-bulletin__publish` 投放。
   你交的是**数据**，不是 HTML/CSS：版式、字号、配色由技能统一决定，
   这样屏幕上那份和用户另存下来的 DOCX 才是同一份东西。
5. 会话里只会出现一个「打开文档」按钮，那是唯一入口：不要再调用 `render_ui`，
   不要重造按钮或链接，也不要提及下载或附件。回复一两句说明这份文档写了什么、
   提示窗口里可以另存为 DOCX，并主动告诉用户**可以直接说哪里要改**。

## 把对话里已经展示过的内容做成文档

用户说「把上面的内容生成一份 word 文档」「按刚才那些图表出个文档」时：

- **原样搬运，不要重新取数。** 你刚才在对话里画的每一张图、每一张表、每一组卡片，
  都已经是一份结构化数据了。把它照抄进 `doc.blocks`：
  - 对话里的图表（`{"type":"chart", ...}`）→ 文档里的 `chart` 块，
    `type` 字段改名叫 `chartType`，`labels` / `series` 一个数字都不许动；
  - 对话里的表格 → `table` 块，`columns` / `rows` 原样；
  - 对话里的指标卡 → `metrics` 块；键值清单 → `keyValue` 块；
  - 对话里的文字结论 → `paragraph` / `list` / `callout` 块。
- **顺序按对话里出现的顺序**，用户看到的是同一份东西换了个载体，不是重写。
- 数值、单位、口径、时间范围一律不改。要补的只有文档需要而对话里没有的东西：
  标题、必要的过渡句、数据出处。
- 只有用户明确要求「重新查一遍最新的」时才重新取数。

## 修改

用户提出修改后：以上一次 `publish` 的 `doc` 对象为底稿，只改他点到的地方，
其余字段逐字保留，然后整份重发再调一次 `publish`。不要图省事重写全文——
用户没提到的段落被改掉就是缺陷。若上一版已不在上下文里，直说并重新生成一版。
