# 04 · 写作规约

约束 Markdown 正文的具体写法。审稿按此逐条核对。

## 1. 章节骨架

每一章统一用这个骨架（模板见 [../01-architecture/03-page-templates.md](../01-architecture/03-page-templates.md)）：

```markdown
# <章标题>

<1-2 句：这章解决你什么问题。不要写"本章将介绍…"这种废话开场。>

## 你能做什么 ← 能力清单，3-6 条，每条一行

## <小节 1：一个具体任务>

步骤 1 / 2 / 3 + 截图

## <小节 2：…>

## 网页版与扩展版的差别 ← 强制小节，没有差别也要写"两者一致"

## 出问题了怎么办 ← 强制小节，至少 2 条常见故障
```

「网页版与扩展版的差别」和「出问题了怎么办」是**强制小节**，缺一即不合格。

## 2. 步骤写法

```markdown
1. 在页面右下角点 **展开 AI 助手**，打开对话抽屉。
2. 在输入框里粘贴：`分析当前迭代的燃尽情况，判断能否按时收尾，说明依据和风险`
3. 按回车。助手会先显示 **思考中…**，随后逐段输出结论。

![迭代燃尽分析的运行过程](/docs-assets/chat/burndown-run.png)
```

规则：

- 序号步骤只写**用户的动作**；系统的反应写在同一步骤的后半句或下一句。
- 界面元素用 `**加粗**`，用户要输入的原文用 `` `行内代码` ``。
- 一组步骤不超过 7 步，超了拆小节。
- 每个小节**至少一张截图**，截图紧跟在它说明的步骤之后，不要攒到节尾。
- 图注写「这张图证明了什么」，不要写「如图所示」。

## 3. Markdown 元素约定

| 元素   | 用法                                                 | 限制                               |
| ------ | ---------------------------------------------------- | ---------------------------------- |
| 标题   | 只用 `##` 与 `###`                                   | 不用 `####` 及更深；深了说明该拆章 |
| 表格   | 对比、清单、参数说明                                 | 列数 ≤ 4，手机上会挤               |
| 提示块 | `> **提示**：` / `> **注意**：` / `> **仅扩展版**：` | 三种，不自造第四种                 |
| 代码块 | 仅用于：技能内容、用户要复制的提示词                 | **禁止** TS/JS 调用示例            |
| 折叠块 | 长清单（如 console 25 页速查）                       | 正文主线不折叠                     |
| 图片   | `![说明](/docs-assets/<章>/<名>.png)`                | 命名见 03-visuals/02               |

`> **仅扩展版**：` 这个提示块是本次文档的特色标记，
凡是网页版没有的能力都要用它标出来，让读者一眼可辨。

## 4. 长度控制

| 类型             | 目标篇幅     | 上限 |
| ---------------- | ------------ | ---- |
| 入门类章节       | 600-1000 字  | 1500 |
| 功能类章节       | 1000-1800 字 | 2500 |
| console 单页说明 | 300-600 字   | 800  |
| 场景实战         | 800-1200 字  | 1800 |

超上限就拆。文档模块是网页阅读，不是 PDF 手册，长页面没人读完。

## 5. 交叉引用

- 同一概念只在**一个地方**详细讲，其他地方链接过去。
  例：授权机制在「页面操作」章详讲，console 的信任设置页只写「这里的开关影响
  <链接>页面操作</链接>时是否每次都问你」。
- 引用格式：`[授权与撤销](/docs/page-actions#authorization)`。
- 禁止「如前所述」「详见后文」这类无链接的指代。

## 6. 关于不确定性的表述

模型行为有随机性，文档必须诚实：

| 场景         | 正确写法                                       | 错误写法               |
| ------------ | ---------------------------------------------- | ---------------------- |
| 结果可能不同 | 「助手可能选择不同的技能，结论措辞也会有差异」 | 「助手会输出如下结果」 |
| 需要多轮     | 「如果一次没说清，助手会弹卡片追问」           | 「助手总能一次理解」   |
| 会失败       | 「网络中断时这一步会失败并显示重试」           | 不提                   |

截图里的模型输出**必须标注是一次真实运行的示例**，
加图注：`示例运行结果，你的实际输出会有所不同。`

## 7. 提示词的呈现

Demo 的快捷提示是现成的高质量例子（`src/demo/webskill/quickPrompts.ts`），
文档里引用时：

- 用行内代码或代码块**原样**给出，方便读者复制。
- 中文文档用中文提示词，英文文档用英文提示词——
  Demo 的快捷提示里两种语言都有，不要机翻。
- 每个提示词后面用一句话说明「它会触发什么」，让读者知道为什么这么写。

## 8. 禁止事项汇总

1. 禁止写没有在 Demo 或扩展里实际验证过的行为。
2. 禁止出现 TS/JS 代码示例、API 名、类型名、包名（`@webskill/*`）。
3. 禁止 emoji。
4. 禁止「本章将介绍」「综上所述」「随着 AI 的发展」这类填充句。
5. 禁止只写中文不写英文（或反之）。
6. 禁止在正文里写死颜色/尺寸等实现细节。
7. 禁止把 SDK 文档的段落直接搬运——那是给实现者看的。
