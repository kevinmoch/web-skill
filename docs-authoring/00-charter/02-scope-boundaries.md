# 02 · 范围边界

## 1. 写什么

| 域             | 范围                                  | 说明                                 |
| -------------- | ------------------------------------- | ------------------------------------ |
| chatbot 网页版 | **全部**用户可见能力                  | 以站点 `/demo` 内嵌的助手抽屉为准    |
| chatbot 扩展版 | **全部**用户可见能力 + 与网页版的差异 | 以 `examples/browser-extension` 为准 |
| console        | **全部** 6 组 25 页                   | 每页至少讲清 purpose + 主操作        |
| Demo 实例      | 作为全书统一例子                      | 7 个屏、13 个内置技能、8 个页面工具  |

覆盖度要求是**穷尽式**的：console 的 25 个页面一个都不能少，
chatbot 的 26 个文案域都要有归宿（可以合并讲，但不能没人管）。
清单化方法见 [../04-sourcing/02-extraction-recipes.md](../04-sourcing/02-extraction-recipes.md)。

## 2. 不写什么

以下内容**明确排除**，本次一律不写，也不要「顺便提一嘴」：

| 排除项                                                      | 原因         | 若确有必要                                                   |
| ----------------------------------------------------------- | ------------ | ------------------------------------------------------------ |
| SDK 安装、依赖、版本                                        | 后续单独规划 | 留一句「面向开发者的接入文档另见（待发布）」                 |
| 任何 API / 函数 / 类型签名                                  | 开发者视角   | 无                                                           |
| 宿主接入步骤（`createChatbot`、`ThemeScope`、runtime 装配） | 开发者视角   | 无                                                           |
| 架构实现原理（包依赖、模块划分、数据流实现）                | 开发者视角   | 用户视角的「原理图」可以画，但讲的是**行为**不是**代码结构** |
| 模型供应商申请 API Key 的商务流程                           | 与产品无关   | 设置页讲「在哪填」即可                                       |
| 部署、CI、发布流程                                          | 无关         | 无                                                           |

### 「原理图」的边界

用户视角也需要原理图——但画的是**用户能观察到的因果链**，不是代码调用链。

> ✅ 允许：`你的提问 → 助手判断需要哪个技能 → 弹授权卡 → 你允许 → 技能在沙箱里
跑 → 结果回到对话`（用户每一步都能在界面上看到）
>
> ❌ 禁止：`Chatbot → useChatEngine → agentLoop → ToolSource → SkillRuntime`
> （用户永远看不到这些名字）

判别法：图里出现的每个节点，用户要么能在界面上看到它，要么能感知到它发生了。

## 3. 与 SDK 仓库既有文档的关系

SDK 仓库 `docs/` 下有大量文档（`0.0.2` 到 `0.19.0` 的需求/设计分册）。
它们的定位与本次**完全不同**：

|      | SDK `docs/`              | 本次文档模块     |
| ---- | ------------------------ | ---------------- |
| 读者 | 实现者、接入方           | 终端用户         |
| 内容 | 需求、验收标准、设计决策 | 怎么用           |
| 语言 | 中文为主，含大量类型签名 | 中英双语，零代码 |

**它们是取材源，不是可复制的内容。** 需求分册里的「验收标准」往往描述了
一个用户可见行为，这部分可以转写；但设计文档里的模块划分、接口定义一律不取。

唯一例外是 `verify/` 目录——它写的就是人工操作步骤与观察判据，
可以近乎直接转写为用户文档（改文风即可）。见
[../04-sourcing/01-source-map.md](../04-sourcing/01-source-map.md) §2。

## 4. 版本基线

写作时锁定当前已发布版本，并在文档模块首页标注：

- `@webskill/sdk` 0.19.0
- `@webskill/chatbot` 0.16.0
- `@webskill/console` 0.16.0

界面会随版本变化，因此：

- 截图必须在**同一次会话、同一个版本**下拍完，避免新旧界面混杂。
- 文档正文避免写死版本号（除首页基线声明外），以免每次发版全文失效。
- 若某功能标注为实验性/后续版本，查 `docs/deferred-items.md` 确认是否真的可用，
  **不要写还没实现的能力**。

## 5. 范围争议的裁决

写作中遇到「这算不算范围内」的争议，按此顺序裁决：

1. 用户在界面上能看到 / 能操作它吗？不能 → 不写。
2. 能在 `/demo` 或扩展里复现吗？不能 → 不写（或降级为一句限制说明）。
3. 讲清它需要引入代码概念吗？需要 → 换角度重写，仍需要 → 不写。

三关都过才写。裁决结果记入 `.work/scope-decisions.md`，避免反复摇摆。
