# 01 · 读者与文风

## 1. 读者画像

文档模块的唯一目标读者：

> **一个正在使用某个业务系统的普通用户，这个系统里嵌了 WebSkill 助手；
> 或者一个刚装上 WebSkill 浏览器扩展的人。**
> 他不写代码，不关心 SDK，只想知道「这个助手能帮我干什么、我该怎么让它干」。

推论：

- 他**不知道**什么是 MCP、工具调用、agent loop、沙箱。这些词出现时必须先用一句
  大白话解释，或者干脆换成他能懂的说法。
- 他**会**关心：安全吗？我的数据去哪了？它会不会乱点我的页面？为什么这次没成功？
- 他**不会**打开 DevTools，不会读 JSON，不会改配置文件。
- 他能接受「点这里 → 看到什么」的操作指引，不能接受「系统会通过 X 机制完成 Y」。

## 2. 视角判别标准

这是本次最容易翻车的地方。用下面这把尺子逐句量：

| 判据       | 用户视角（要）                       | 开发者视角（不要）             |
| ---------- | ------------------------------------ | ------------------------------ |
| 句子主语   | 「你」/「助手」                      | 「宿主」/「SDK」/「运行时」    |
| 动词       | 点击、输入、勾选、看到、拖动         | 注册、注入、实例化、挂载、配置 |
| 名词       | 按钮、面板、卡片、开关、页签         | 组件、接口、参数、回调、store  |
| 回答的问题 | 我怎么做到 X                         | X 是怎么实现的                 |
| 出现代码   | 只在「技能编辑器」章允许出现技能内容 | 任何 TS/JS 调用示例            |

**一句话测试**：把句子念给一个不写代码的同事听，他能照着做吗？
不能就是写错了视角。

### 边界情况的处理

有些概念绕不开（例如「技能」「工具」「授权」）。处理原则是
**先给用户能感知的现象，再给名字，最后才给一句原理**：

> ✅ 助手在回答前会先弹出一张卡片，让你确认它要做的操作——比如「即将在页面上
> 提交表单」。你点「允许」它才会动手。这张卡片叫**授权卡**。之所以要你确认，
> 是因为这类操作会真的改变页面内容，无法自动撤销。

> ❌ `PageActionConsent` 在执行 `act_on_page` 前会触发 consent 回调，
> 宿主可实现记住策略。

## 3. 文风

- **第二人称，中文简体为主，英文版同步**。称呼读者用「你」，不用「用户」「您」。
- **短句。** 一句话讲一件事。信息密度高的内容用表格或列表承载，不要堆长段。
- **动作前置。** 先说做什么，再说为什么。`点「新对话」可以清空上下文重新开始`
  好过 `由于上下文会累积，因此提供了新对话功能`。
- **不用营销词。** 禁止「强大」「智能」「一键」「赋能」「无缝」「极致」。
  能力靠具体描述体现，不靠形容词。
- **不吹保证。** 不写「永远不会出错」「100% 准确」。模型有不确定性，
  该写「如果结果不对，你可以…」。
- **不用 emoji。**
- **可验证。** 每个「你会看到 X」都必须是截图或 Demo 里真实存在的 X。

## 4. 中英双语要求

站点已有 `src/locales/{zh,en}.json`（198 键），文档模块的**每一句面向用户的文案
都必须两份齐全**。这不是可选项，见
[../01-architecture/02-site-integration.md](../01-architecture/02-site-integration.md)。

英文版不是机翻中文版：

- 英文是**平实的技术英语**，不是中式英语直译。
- 术语用 SDK 源码里已有的英文原词（`packages/chatbot/src/i18n.ts` 的 `en` 段
  是权威词库），不要自造。例：会话叫 `Sessions` 不叫 `Conversations`；
  快捷提示叫 `Quick prompts`；授权卡在源码里的表述以 `interaction.*` 键为准。
- 中英两版的**结构必须一致**（相同的小节数、相同的图、相同的截图位），
  便于对照与审阅。

## 5. 每章必须回答的三个问题

任何一章写完，读者应当能回答：

1. **这个功能解决我什么问题？**（价值，1-2 句，放开头）
2. **我具体怎么操作？**（步骤 + 截图）
3. **什么时候它不管用 / 出问题了怎么办？**（限制与排错，放结尾）

第 3 点最常被漏掉。本项目里几乎每个能力都有明确边界
（网页版不能跨标签页、沙箱里的脚本不能访问网络、模型不支持图片时附件会被拒等），
这些边界写清楚了，文档才可信。
