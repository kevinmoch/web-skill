## 第 5 章 · 提问、回答与打断 `chat-basics`

### 目标

读者会发消息、会中途停止、会重试、会编辑已发出的话、会复制和删除消息。

### 大纲

```
# 提问、回答与打断
## 发出第一条消息
## 回答是一段段出现的        ← 流式
## 中途叫停                  ← Stop，且已生成内容会保留
## 让它重来一次              ← 重试
## 改一句刚才说的话          ← 编辑消息
## 复制与删除                ← 含删除后的撤销
## 上一轮没做完怎么办        ← 中断恢复 banner
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

**「中途叫停」必须写清一个关键事实**：点停止后，**已经生成的正文会保留**，
不会被清空；正文与中止提示是两个独立部分，中止提示默认可见。
（依据 `verify/agent/02-chat-basics.md` A-07 与 `03-message-fidelity.md` A-18。）

**「删除」要写撤销**：删除后出现提示，提示消失前可撤销
（`message.deleted.description`：本提示消失后即永久移除；`toast.undo`：撤销）。
这是用户最容易误操作的地方，必须写明。

**「上一轮没做完」** 讲中断恢复：界面顶部出现
「你有一轮未完成的对话 / 上一轮运行在等待输入时中断。点击恢复，从中断处继续。」
配 **恢复** 按钮（`banner.*`）。

## 第 6 章 · 管理会话 `sessions`

### 目标

读者会新建、切换、搜索、重命名、归档、删除会话，并知道会话与上下文的关系。

### 大纲

```
# 管理会话
## 什么是一次会话          ← 讲清上下文边界，这是读者最大的困惑
## 新建与切换
## 找回以前的对话          ← 搜索 + 加载更早
## 重命名、归档、删除
## 关掉页面会丢吗          ← 持久化
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

**「什么是一次会话」是本章价值最高的一节**。读者最常见的困惑是
「为什么助手忘了我刚才说的」或「为什么它还记得上一个话题」。要讲清：

- 同一会话内，助手记得前面说过的话。
- 换会话 = 从零开始，互不影响。
- 什么时候该开新会话（换话题、上下文太长、结果被前文带偏）。

界面措辞（`session.*`，24 条）：会话 / 会话列表 / 新对话 / 搜索会话… /
重命名 / 归档 / 取消归档 / 删除 / 已归档 / 加载更早的会话。
删除确认文案要写明：**对话及其运行记录一并移除，且不可撤销**
（`session.delete.confirmDescription`）——与消息删除可撤销不同，别写混。

`session.skipped`（这些会话文件无法读取，已跳过：{files}）
是一个真实会出现的异常提示，放到「出问题了怎么办」。

### 目标

读者理解技能是什么、怎么让助手用上、怎么确认它用了哪个。

### 大纲

```
# 技能：让助手会干专业活
## 技能是什么              ← 用 Demo 的 13 个内置技能举例
## 怎么触发一个技能        ← 自然语言，不需要记命令
```

### 内容要点

#### ★「两种技能：现成的和现做的」

**这一节是第 7 章最有实用价值的部分，不能省，也不能只写一句带过。**

Demo 的大屏 / 公文 / 幻灯片三类产物**各有两个技能，成对存在**：

| 你要的东西 | 现成的（固定模板） | 现做的（动态构建）  |
| ---------- | ------------------ | ------------------- |
| 大屏       | `agile-ops-screen` | `authored-screen`   |
| 公文       | `quality-bulletin` | `authored-bulletin` |
| 幻灯片     | `agile-slide-deck` | `authored-slides`   |

**两者对用户的差别**（这才是读者要知道的，不要写成技术对比）：

|                    | 现成的         | 现做的               |
| ------------------ | -------------- | -------------------- |
| 出活速度           | 快、稳         | 慢一些               |
| 取哪些数据         | 写死的全量口径 | **按你说的范围取**   |
| 版式 / 分区 / 配色 | 改不动         | **你说了算**         |
| 幻灯片页数         | 写死           | **由内容决定**       |
| 生成后想改         | 改不了         | **说一句就重做一版** |

**「什么时候会用现做的」——给读者三条可判断的信号**
（这三条直接来自技能自己的选用规则，是助手真实的判断依据）：

1. 你**限定了数据范围**：「当前页面的」「只要这一类」「这段时间的」。
2. 你**指定了内容或形式**：要看哪几个指标、怎么分区、什么配色、分几页讲。
3. 你**看完之后提出了修改**——哪怕只是「配色换成浅色」。

只有当你**笼统地**要一份标准产物（既没限范围也没提要求）时，
才会走现成的那个，因为它更快更稳。

**必须讲清的一个因果**（否则用户会困惑）：
对「现成的」产物提修改要求时，助手不是在原件上改，而是**改用「现做的」重做一版**。
所以你会看到它重新取了一次数、重新出了一份，而不是原地微调。
这不是它没听懂，是固定模板确实改不动。

**写法建议**：用一组对照例子讲，比讲规则有效得多。

```
「给我一块运营大屏」              → 现成的，最快
「给我一块只看当前页面需求的大屏」 → 现做的（限定了范围）
「大屏做好了，把缺陷那块换成折线图」→ 现做的（重做一版）
```

**不要写**：技能名的匹配机制、`description` 字段、路由算法。
读者只需要知道「我怎么说，会得到什么」。

#### ★「把这次对话变成一个技能」

**此前整块遗漏。** 站点源码把它称作「本 demo 的卖点之一」
（`src/demo/webskill/runtime.ts:70`），Demo 里**默认开启**。

用户视角：**你带着助手把一件复杂的事做成了，可以把这个过程存下来，
下次一句话就能重跑。** 这是产品从"每次都要重新解释"变成"越用越顺手"的关键。

必须写清的四件事：

**一、它会先给你看，再问你要不要存。**
确认文案（`skillGeneration.confirm`）逐字如下，**必须原文引用**：

> 将本次对话保存为技能「{name}」？{description}
> 它将提交审核，不会直接启用。请逐字检查下方预览，确认没有不应被保存的内容。

**二、存下来不等于能用。**
它进的是**审批队列**，要有人审过、发布了才生效
（`candidate.submitted`：「「{name}」已提交待审。审批并发布后才能使用。」）。
这一条不写清楚，用户会以为存完就能用，然后发现调不动。

**三、你可以直接跳过去看。**
提交后给的是**候选 ID**，可以复制（`candidate.id.copy` / `candidate.id.copied`），
也可以直接点「去审批」（`candidate.review`）跳到控制台的审批队列。
这里要给第 21 章的链接。

**四、存之前请你自己看一眼。**
确认文案里那句「请逐字检查下方预览，确认没有不应被保存的内容」
**是给用户的责任提示，必须原样传达，不能弱化成"可以检查一下"**。
对话里可能有你不想沉淀下来的东西（具体的人名、内部数字、一次性的口令）。

**这一节与第 21 章、第 30 章形成闭环**，三处的说法必须一致：
本章讲"能存"，第 21 章讲"审批怎么走"，第 30 章讲完整场景。

> **写作提醒**：这个能力有个开关（控制台 → 设置 → 智能体运行时 →
> 「技能自动生成」）。Demo 默认开着，但**别的系统可能是关的**，
> 要写一句「如果你没看到这个入口，可能是你所在的系统关掉了它」。

**「怎么知道用了哪个」**：消息上的技能标记，以及
「本轮运行使用的技能」（`message.skillsUsed`）、
运行步进里的「已激活技能：{name}」（`trace.skill`）。

**「技能跑在哪里」只写一句话**的安全说明：技能脚本在隔离的沙箱里运行，
碰不到你的页面和数据；详细的沙箱设置在第 23 章。

## 第 8 章 · 助手向你要东西：六种交互卡 `interactions`

### 目标

读者遇到任何一种卡片都知道那是什么、该怎么应答、不应答会怎样。

### 大纲

```
# 助手向你要东西
## 为什么会弹卡片
## 需要回答
## 请确认
## 需要补充信息
## 选择一个选项
## 它替你猜的那个值      ← 建议值：怎么来的、为什么不会自动填进去
## 需要授权              ← 最重要，链接到第 14 章
## 需要一个文件
## 不理它会怎样          ← 超时会终止运行
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

六种卡片的标题必须逐字使用（见
[../00-charter/03-terminology.md](../00-charter/03-terminology.md) §2）。
每种给：什么时候出现、卡上有什么、你该做什么、一张截图。

**「不理它会怎样」是必写项**：表单未及时提交，运行会停止
（`run.terminated.interactionTimeout`：表单未及时提交，运行已停止）。
读者常把卡片晾着然后困惑为什么没结果。

`interaction.*` 是第二大文案域（62 条），
写作前**务必先导出全部 62 条**（配方见 04-sourcing/02 §1.2），
里面有大量按钮名、状态名、校验提示，不导出必写漏。

**★「它替你猜的那个值」必须单独成节。**
「需要回答」和「选择一个选项」这两种卡上，有时会多出一行**建议值**和一个采纳入口。
读者第一次看见会立刻产生两个疑问——它凭什么知道、它是不是已经替我填了——
两个都要正面回答，而且答案都在读者这边：

- **它不会替你填。** 建议值只是摆在那里给你看，旁边有一个采纳的入口；
  **你不点，这个值就不算数**，提交上去的仍然是空的。
  这一条是渲染层的硬约束（`InteractionSuggestion` 注释：「**不会预填进控件**：
  渲染器只能展示它并提供「采纳」入口，用户确认后才算填写」），不是建议做法。
  别写成「它会自动填好，你检查一下就行」——那是错的，也会让读者误以为不看就会被提交。
- **它会告诉你凭什么这么猜。** 建议值带一条**建议依据**（`reason`），
  比如「你最近几次都选了这个」。写作时要点出这条依据的用途：
  它不是解释给你听着玩的，**是让你判断这次要不要采纳**——
  依据说的是三个月前的事，你就该跳过它。
- **猜不出来它就不猜。** 没有依据支撑时，字段**留空**，不会编一个看起来合理的值。
  这是写死在系统提示里的一条规则（`USER_PROFILE_NO_INVENTION_RULE`：
  「没有相关条目就省略建议、把字段留空，绝不臆造」）。
  这一条要正面写出来，因为它正好回答了下一个问题——

**必须写「为什么我一条建议都没看到」。**
建议值来自**它记住的你**，而它一开始并不认识你。
新用户头几次用，卡片上什么建议都不会有，这是正常的，不是功能坏了。
用得越久、你答过的问题越多，它猜得越准。
不写这一句，读者会拿着一张没有建议的卡片去怀疑自己装错了。

这些「记住的你」存在本机，**可以逐条查看、逐条删除**——
指向第 23 章（设置 › 隐私与用户画像）讲怎么管，指向第 33 章讲它到底存了什么、会不会外发。
本章只负责让读者看懂卡片上多出来的这一行。

## 第 10 章 · 附件、图片、语音与拍照 `attachments`


### 内容要点

#### ★「你能传哪些文件」

**此前写成「文本 / 图片 / 文件三类」是错的，实际是四类**
（`composer.attachment.kind.*`：文本 / 图片 / 文件 / **文档正文**）。
更要命的是没列具体格式——读者因此不知道自己能传 Excel。

**必须给出这张表**（依据 `packages/core/src/attachment/kind.ts`）：

| 界面上显示 | 你可以传                           |
| ---------- | ---------------------------------- |
| 图片       | png、jpeg、webp、gif               |
| 文本       | txt、md、csv、json、log、yaml、yml |
| 文件       | pdf                                |
| 文档正文   | **docx、xlsx**                     |

**Excel 和 Word 能传，这是读者最想知道的一条，不能埋在正文里。**

#### 「传进去之后会发生什么」

四类的处理方式不同，且**用户能观察到差别**：

| 类型                  | 处理方式                               | 用户需要知道的                 |
| --------------------- | -------------------------------------- | ------------------------------ |
| 图片                  | 直接发给模型                           | 可能被压缩；每条消息有张数上限 |
| 文本                  | 作为文字发                             | **超长会截断**（上限 32 KB）   |
| 文件（pdf）           | 整份发给模型                           | 需要模型支持                   |
| 文档正文（docx/xlsx） | **先在你的浏览器里抽成文字，再发文字** | 原文件不会整份发出去           |

最后一行有**隐私价值**，第 33 章要呼应：
docx/xlsx 是在本地抽取的，发出去的是抽出来的文字，不是原文件。

字符上限用 `ATTACHMENT_TEXT_LIMIT` 的实测值（当前 32 KB），**现取现用**。

张数上限的提示原文是 `attachment.imagesDropped`：
「每条消息最多发送 {limit} 张图片。未发送：{names}」——
要写明**超出的图片会被丢掉并列出名字**，不是静默忽略。

## 第 11 章 · 看懂助手在做什么 `transparency`

### 目标

### 大纲

```
## 查看追溯与运行 ID

## 出问题了怎么办
```

### 内容要点

**六个阶段**（`status.*` / `trace.phase.*`，界面原词）：

| 阶段 | 界面文案      | 含义（用户语言）                 |
| ---- | ------------- | -------------------------------- |
| 路由 | 路由中        | 正在判断该用哪个技能或工具       |
| 激活 | 激活技能      | 已选定技能，正在装载             |

（措辞取自 `run.terminated.*`）+ 对应处理建议：

| 界面提示                         | 用户该怎么办                                         |
| -------------------------------- | ---------------------------------------------------- |
| 运行已被你中止                   | 无需处理，可重试                                     |
| 达到轮次上限，运行已停止         | 任务太复杂，拆成几步说；上限可在设置里调（第 23 章） |
| 达到时长上限，运行已停止         | 同上                                                 |
| 模型请求失败，运行已停止         | 检查模型配置/网络（第 12、32 章）                    |
| 表单未及时提交，运行已停止       | 卡片要及时回答（第 8 章）                            |
| 生命周期钩子失败，运行已停止     | 联系提供该系统的人                                   |
| 多次调用不存在的工具，运行已停止 | 换个说法重试；可能是技能与当前页面不匹配             |
| 运行未正常结束                   | 重试；仍失败则查运行记录（第 20 章）                 |

**工具调用**：显示「{count} 次工具调用」，每次有状态
运行中 / 已完成 / 失败 / **被策略拒绝** 和耗时、参数。
「被策略拒绝」要重点解释——它说明系统有安全边界，不是所有请求都会被执行。

**任务清单**（`todo.*`）：待开始 / 进行中 / 已完成，
带进度 `{done}/{total}`，还可能显示「已委派给 {技能名}」。

**★「已委派给…」要展开写一小段，不能只列出来。**
读者看到这行会困惑：「它怎么把活派给别人了？」

要讲清三点：

1. **这是它自己在分工**：复杂任务里，助手会把某一步交给一个更专门的技能去做。
   你不需要做任何事。
2. **是一步一步来的，不是同时开工**。派出去的那一步做完，
   它才继续下一步（依据 `docs/deferred-items.md` D26：委派是串行的）。
   所以看到「已委派」时，等就对了。
3. **有一个副作用要提醒**：委派出去做的那部分，
   在「把对话存成技能」时可能**不算作本次对话做过的事**，
   会导致存技能失败（依据 D62）。
   遇到时的建议：不带委派重做一次关键步骤，再存。

> 第 3 点是 `docs/deferred-items.md` 里记录的**已知限制**，不是 bug。
> 按边界情况的写法处理：描述现象 → 说明这是什么 → 给出可行的做法。
> **不要**写成"这是个缺陷，未来会修"——用户不关心路线图，只关心现在怎么办。

这一小段与第 7 章「把这次对话变成一个技能」相互引用。

**运行 ID**：可复制，用于在 console 的运行记录里精确定位（链接第 20 章）。

## 第 12 章 · 选择模型 `models`

### 目标

读者会切换模型、看懂模型能力标记，知道模型选择会影响什么。

### 大纲

```
# 选择模型
## 在哪儿切模型
## 模型能力标记是什么意思    ← 可用工具 / 可传图片
## 没配模型会怎样
## 演示模型
## 换模型会影响什么          ← 能力、速度、结果风格
## 浏览器自带的 AI
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

**模型能力标记**（`capability.*`，5 条）：
「模型能力」分组下显示 可用工具 / 无工具、可传图片 / 不可传图片。
要讲清后果：**模型不支持工具时，助手就不能调用技能和读页面**，
只能纯聊天。这是读者遇到"助手突然变笨了"的头号原因。

**没配模型**（`composer.noModel.*`）：
「尚未配置大模型」+ 「配置大模型」按钮 → 跳到第 23 章的模型配置。
还有一种是条目不可用（`composer.model.unconfigured`：
该条目既没有 API 密钥也没有基础地址）。

**演示模型**（`composer.model.demo`）：Demo 里会用到，要说明它的用途与局限。

**浏览器自带的 AI**：见 `verify/human/02-chrome-builtin-ai.md`。
写之前**先确认它在当前版本可用**（查 `docs/deferred-items.md`），
不可用就不写。
