## 第 13 章 · 让助手读当前页面 `page-perception`

### 目标

读者理解助手能读到什么、读不到什么，并会控制读取范围。

### 大纲

```
# 让助手读当前页面
## 不用复制粘贴            ← 价值开场
## 怎么让它读              ← 自然语言即可
## 它读了哪些内容          ← 界面会明示范围
## 哪些内容它读不到        ← 密码框等，建立信任
## 页面里的图片            ← 图像抓取，可关闭
## 网页版与扩展版的差别    ← 范围差异，重点
## 出问题了怎么办
```

### 内容要点

**「它读了哪些内容」——界面是明示的**，这点要突出，是信任的基础。
运行时会显示（`perception.*`，5 条）：

| 界面提示                          | 含义                 |
| --------------------------------- | -------------------- |
| 正在读取页面内容（区域：{scope}） | 明确告诉你读的是哪块 |
| 已排除：{scope}                   | 明确告诉你哪块没读   |
| 已抓取 {count} 张图               | 图像也进了上下文     |
| 略过 {count} 张                   | 有图被跳过           |
| {count} 张读取失败                | 有图没读成           |

**「哪些内容它读不到」是本章的信任锚点**，必须写：

- **密码框里的值不会被读取**（依据扩展 e2e AC-14.8：密码框的值不出现在感知结果里）。
- 被排除的区域不会被读取，界面会告诉你排除了什么。
- 关闭图像抓取后，一张图都不会外发，但文字仍能读
  （依据 AC-16.2）——这个组合很重要，说明控制是精细的，不是一刀切。

**形态差异**：

|                      | 网页版                   | 扩展版                                   |
| -------------------- | ------------------------ | ---------------------------------------- |
| 能读的页面           | 只有助手所在的这一个页面 | 你打开的任意网页                         |
| 页面里嵌的第三方框架 | 受限                     | 能读到多层嵌套里的跨源内容（文字和图片） |

扩展版能读三层嵌套的最内层跨源帧（AC-16.1 / 16.16）——
这是很强的能力，**必须紧跟着写清它受哪些约束**（密码框不读、图像可关）。

## 第 14 章 · 让助手操作页面 `page-actions`

### 目标

读者敢用、也会用页面操作：**知道哪些事它会先问你、哪些不会**，
知道怎么记住、怎么撤销。

### 大纲

```
# 让助手操作页面
## 它能替你点什么、填什么
## 哪些事它会先问你        ← ★ 分级，此前写错成「每步都问」
## 动手之前先问你          ← 授权卡，本章核心
## 它怎么知道自己点到哪了  ← ★ 去向、后退、滚动
## 让它别每次都问          ← 记住 / 不再询问
## 反悔了怎么办            ← 撤销，链接第 23 章信任设置
## 有些事它不会做          ← 被策略拒绝
## 登录状态下的操作
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

#### ★「哪些事它会先问你」

**此前本章（以及全书）把页面操作写成「每一步都要你同意」，这是错的**，
而且这个错误会让读者以为「填一张 10 个字段的表要点 10 次允许」，
从而认定这个功能不实用。**必须纠正。**

真实规则（依据 Demo 宿主 `src/demo/webskill/actions.ts`）：

| 它要做的事                     | 会不会先问你     | 为什么                             |
| ------------------------------ | ---------------- | ---------------------------------- |
| 往输入框里填字、在下拉里选一项 | **不问，直接做** | 还没提交，填错了你看得见也改得回来 |
| 点按钮、提交表单、上传文件     | **一定先问**     | 这些会真的写进系统                 |

**这条规则是本章最能建立信任的一句话**，要写在显眼处：

> 它可以自己把整张表填好，但**按下"提交"之前一定会停下来问你**。

配套要写两点：

1. **拒绝不会毁掉整轮任务。** 你点「拒绝」，只是这一个动作没做成，
   助手会继续往下走，这次拒绝也会记进审计（第 22 章）。
2. **同意过的可以「不再询问」。** 确认卡上有这个选项，
   勾了之后同类操作就不再打断你。**它必须和撤销成对写**——
   撤销在控制台（第 23 章信任设置），而且**撤销立刻生效**，
   不需要重新加载页面。

> **形态提醒**：免确认的动作种类**由你所在的系统决定**，不是助手自己定的。
> 本书用 Demo 的设定举例，要补一句「别的系统可能划得更严」，
> 避免读者到了别处发现对不上。

---

**「动手之前先问你」是本章的信任基石**，要讲清授权卡上有什么：
它要做的操作是什么、在哪个页面上做、允许/拒绝、以及"记住"的选项。

**「记住」与「撤销」成对写，不能只写一半。**
依据扩展 e2e AC-14.9 / 14.10 / 14.11：确认卡、记住、撤销都存在，
且**密码框永不记住**。撤销的位置在 console（第 23 章信任设置），要给链接。

**「有些事它不会做」**：对应工具状态「被策略拒绝」。
从 `packages/agent/src/pageAction/policy.ts` 里取出被拒绝的类别，
翻译成用户语言（例如：不在允许范围内的目标、危险操作等）。
**只写结论不写实现**。

**「它能点什么」可以写得具体一点**，因为这决定了读者的预期：
不只是标准按钮——没有 role 的列表项、SVG 图标也能被识别和点击
（依据 AC-11.6、AC-12.6）。这解释了「为什么它能点那个看起来不像按钮的东西」。

---

#### ★「它怎么知道自己点到哪了」

**这一节此前遗漏，必须补。** 它解释了三种读者会亲眼看到、
但没有解释就会困惑的助手自主行为，也是第 15 章逐项处理列表的基础。

**一、点完之后它知道去了哪。**
每次操作完成后，助手会得到一个"去向"，共四种情况
（依据 `packages/agent/src/prompts/pageAction.ts` 的四种去向说明）：

| 去向               | 用户看到的               |
| ------------------ | ------------------------ |
| 打开了新页面       | 助手会切过去读那一页     |
| 当前页跳到了新地址 | 助手继续在这一页上读     |
| 弹出了对话框       | 助手在对话框里继续       |
| 页面没有变化       | 助手知道这次点击没起作用 |

**这一段的价值**：读者会问「它点完怎么自己就接着干了」，
答案是它拿得到去向，不需要你指路。**不要写工具名和字段名**，
用「它知道自己点到哪了」这样的话讲。

**二、它会自己按后退。**
助手可以返回上一页，用于「进详情看完 → 回列表 → 看下一个」。
**要提醒读者**：后退也是一次页面操作，同样要经你同意（除非你选了记住）。

**三、它会自己滚动，但不会乱滚。**
只有当页面本身表明还有你看不到的内容时它才滚
（例如列表写着 20 行但只显示了 13 行），**滚到底就停**。
这解释了「它为什么在自己翻屏」，也说明它不会无休止地滚下去。

> 三个动作都要按「现象 → 这是什么 → 一句话原理」的边界情况写法处理，
> 不要写成功能罗列。读者是在遇到了才来看这一节的。

**「登录状态下的操作」**：见 `verify/human/09-oauth-page-actions.md`。
要提醒读者：助手在你已登录的页面上操作，等同于你自己在操作，
所以授权要慎重。

## 第 15 章 · 跨标签页工作（仅扩展版） `tabs`

### 目标

读者会让扩展版助手同时处理多个网页，并清楚它的边界。

### 大纲

```
# 跨标签页工作
> **仅扩展版**：本章讲的多标签页能力网页版没有。
## 一次处理多个网页
## 让它逐项处理一整个列表  ← ★ 本章最有价值的用法
## 助手能用哪些标签页      ← 工作集，边界在这里
## 它一次最多开多少页      ← 容量与撞上限的表现
## 它会抢我的画面吗        ← 不会
## 出问题了怎么办
```

### 内容要点

**章首提示块的措辞要准确。**
不能写成「本章全部内容网页版不适用」——**「逐项处理一个列表」这个用法网页版也有**，
只是做法不同（见下）。准确的写法是「本章讲的**多标签页**能力网页版没有」。

**「助手能用哪些标签页」是本章最重要的一节**，也是最反直觉的：

- 助手只能用**工作集内**的标签页。
- **你自己开的标签页，它枚举不到**（依据 AC-G4：
  用户自己开的标签页模型枚举不到，工作集外的句柄一律结构化拒绝）。
- 切换活动标签页时绑定会跟过去，但**扩展自己的页面不会被接管**（AC-14.6）。

这一节写好了，读者对扩展版的安全顾虑就解决了大半。

**「它会抢我的画面吗」——不会**（依据 AC-G5：
切焦点不动用户的画面，一轮之后活动标签页与窗口焦点原样）。
这是用户最直接的担心，要正面回答。

---

#### ★「让它逐项处理一整个列表」

**这是扩展版最有说服力的能力，此前只用一句「多步自动化」带过，必须展开成独立一节。**

用户视角的描述：给它一个列表，它会**自己一项一项打开、读完、回来、进下一项，
最后把所有结果汇总给你**——中途你不需要做任何操作（依据 AC-G10）。

要写清四件事：

**一、它是怎么做的（一句话，不讲实现）。**
进一项 → 读完 → 回到列表 → 进下一项，循环到做完。
读者需要这个心智模型才能预期它的行为。

**二、可以套几层。**
不止一层——从列表进详情、详情里再进下一级，**至少三层的下钻与逐层回退是支持的**
（依据 0.16.0 分册 16 FR-16.6）。给一个 Demo 里的例子（项目 → 迭代 → 需求详情）。

**三、网页版能做到什么程度**（**这条最容易写错，必须写**）：
网页版没有多标签页，但**在同一个站点内靠"跳转 + 后退"也能逐项处理**
（依据 0.16.0 分册 13：原地跳转的形态也能完成同样的往返）。
网页版做不到的是：跨标签页、跨站点、以及同时留着多个页面对照。

> 这一条是全书最容易把"扩展版更强"写成"网页版完全没有"的地方。
> 写之前回头看 [../04-sourcing/03-web-vs-extension.md](../04-sourcing/03-web-vs-extension.md)。

**四、什么时候会中途收尾。**
见下一节。

---

#### ★「它一次最多开多少页」

**这一节是新增的，用户一定会撞上。**

一轮任务里工作集**最多同时容纳 32 个页面**
（依据 `packages/agent/src/tabs/policy.ts` 的 `TAB_WORKSET_DEFAULT_MAX = 32`；
宿主可调，范围 2 ~ 32）。

**撞上限时用户看到什么**：助手会**在没做完的情况下收尾**，
用已经读到的部分给结论。它**没有办法向你要更多配额**，所以不会提示你去调。

**这一节的实用价值在于教读者怎么办**：
把范围说小一点（「先看前 20 行」「只看这一类」），分两轮跑。

另外两种页面不可用的情况也要写（依据同文件的 `expired` / `unknown`）：

| 现象                             | 是什么                                     |
| -------------------------------- | ------------------------------------------ |
| 刚看过的那一页忽然点不动了       | 那一页已经不在工作集里了，助手会重新读一次 |
| 换了个新对话后它认不出之前的页面 | 页面的引用不跨会话，新对话要重新开始       |

> **数值必须现取现用，不要照抄本手册。** 这三个常量随版本调整过
> （8 → 20 → 32），写作时重新执行：
> `grep -n "TAB_WORKSET_.*MAX" packages/agent/src/tabs/policy.ts`

## 第 16 章 · 产物：大屏、公文、幻灯片与打印 `artifacts`

### 目标

读者会查看、放映、下载、打印助手产出的东西。

### 大纲

```
# 产物
## 助手能产出什么          ← 四类：报告/大屏/公文/幻灯片
## 在对话里打开            ← 打开文档
## 在新窗口里放映          ← 需要你同意才开窗
## 下载到本地
## 打印或存成 PDF          ← 版式会被保留
## 网页版与扩展版的差别
## 出问题了怎么办
```

### 内容要点

**四类产物用 Demo 的技能举例**（与第 7 章的分类保持一致）：
报告（`sprint-progress-report`）、大屏（`agile-ops-screen`）、
公文（`quality-bulletin`）、幻灯片（`agile-slide-deck`）。

**「在新窗口里放映」必须写授权**：
开窗前会有确认卡，**你不同意就不开窗**，且调用方会拿到明确错误
（依据 AC-13.4 / 13.14）。这是产物投放的安全边界。

**「打印或存成 PDF」要写两个真实保证**（来自扩展 e2e）：

- 幻灯片打印时**技能设定的版式（内边距）会被保留**。
- **深色幻灯片打印时不会丢底色**。

这两条很具体，是「产物质量可信」的证据，值得写。

**「下载到本地」**：产物区有 下载 按钮（`result.*`：产物 / 下载 / 文件）。

> **⚠ 这一节只讲「助手做的东西存到你机器上」，不要写成「助手去读你机器上的文件」。**
> 那是方向相反的另一件事，独立在第 17 章。
> 本章的下载**不需要授权**——那本来就是你要的东西；
> 第 17 章的读取**每次都要授权**。把两者混在一起写，
> 读者会以为「下载产物也要审批」或者「读我的文件不用问」，两种误解都很糟。

**站点自身的 `viewer.html`** 就是投放查看器，Demo 的大屏/幻灯片会在那里打开，
截图时注意这是站点的一部分。

## 第 17 章 · 让它看你刚下载的那个文件 `downloaded-files` **仅扩展版**

### 目标

读者知道扩展版可以读取自己下载目录里的文件，
**并且清楚每一次读取都经过了自己点头**。

> **本章与第 16 章方向相反，开篇第一句就要点破。**
> 第 16 章是「它做的东西存到你机器上」，本章是「它读你机器上的东西」。
> 后者的敏感度高一个量级，因此**通篇的重心不是能力，是闸门**。

### 为什么用户要这个

先用一个真实到不用解释的场景开场：

> 你在业务系统里点了「导出 Excel」，文件落进下载目录。
> 现在你想让助手看看那份表——
> 过去你得找到它、拖进对话框；现在你可以直接说「看看我刚导出的那份」。

**省掉的是"翻文件夹"这个动作**，读者一秒就懂。

### 大纲

```
# 让它看你刚下载的那个文件
## 这能干什么              ← 上面那个场景
## 它要问你两次            ← ★ 本章骨架
## 它看得到什么、看不到什么 ← 拿不到路径
## 「不再询问」记住的是什么 ← 粒度要说准
## 能读哪些格式            ← 与手动上传完全一致
## 第一次用要先开个开关     ← Chrome 的限制
## 它知道你下载了东西吗     ← 下载信号
## 出问题了怎么办
```

### 内容要点

**★「它要问你两次」是本章骨架。**
读者的默认预期是「授权一次，之后随便读」。事实不是这样，要写清楚是**两道**：

1. **想看目录里有什么** → 先弹一次确认卡。
2. **想打开其中某一份** → 再弹一次，卡上写明**是哪个文件、多大**。

为什么列个清单也要问，要给出理由，否则读者觉得啰嗦：
**文件名本身就是信息**。`离职证明.pdf`、`体检报告.pdf`——
光是把文件名列出来就已经泄漏了。这句话要写进去，它能让读者理解设计意图，
而不是把第一道卡当成多余的打扰。

**「它看得到什么、看不到什么」要正面写一条读者想不到的保证**：
**助手全程拿不到文件在你磁盘上的位置**。
它拿到的只是一个**取件号**，凭号取件，路径由浏览器扩展自己保管。
所以它既说不出你的用户名，也说不出你把东西放在哪个盘。
读者不会主动问这个，但写出来的信任回报很高。

**「不再询问」记住的是什么——必须写准，这里最容易写宽。**
勾了之后记住的**不是这一个文件**，而是**整个下载目录上的这一类动作**。
界面上的措辞本身就说明了这一点（「以后不再询问「列出下载目录」」/
「以后不再询问「读取下载的文件」」），**写作时直接引用这句原话**，
比自己解释更有说服力。
两类动作**分别记忆**：允许它列清单，不等于允许它开文件。
撤销的地方与页面操作的已记住授权**在同一处**（第 23 章），**撤销立即生效**。

**「第一次用要先开个开关」是本章最容易被跳过、却最会卡住读者的一段。**
Chrome 要求你到 `chrome://extensions` 里，找到这个扩展 → 详细信息 →
打开「允许访问文件网址」。**扩展自己打不开这个开关，必须你亲手开。**

- 这一段要给**分步截图**，这是全书为数不多需要走出产品界面的操作。
- 要写清楚**为什么**要你自己开：这正是浏览器在保护你，
  不是产品设计得麻烦。这么写读者才不会觉得是在被为难。

**「能读哪些格式」直接复用第 10 章的四类表**，一个字都不要改，
并明确写「和你手动上传时能传的完全一样」。
两处写得不一致，读者会以为这里有额外限制。
**图片有一个例外要单独写**：如果当前模型不认图，
那么图片在**列清单的时候就已经标成读不了**，并会告诉你换个模型就行——
不是等你点开了才报错。这个细节体感很好，值得写。

**「它知道你下载了东西吗」——这一节讲的是分寸，不是能力。**
当它自己点了页面上的按钮、结果触发了下载，它会知道**有下载发生了**。
但要紧跟一句限定，否则读者会往最坏处想：

- **它只知道"发生了"，不知道文件叫什么。** 想知道名字，还得走前面那两道卡。
- **只统计它自己那次操作引起的下载。** 你自己在旁边下别的东西，它看不见。

**这一节的落点是"它没有在盯着你的下载目录"**，请把这句话明确写出来。
同理还要写：**它只读，不能改名、不能删除、不能往里写东西**，
**也不会在后台盯着**——只有你开口的时候它才去看。

**默认是关着的。** 出厂状态下这个能力不开，
不开的时候助手**根本不知道有这回事**，不会提出要看你的文件。
「不知道」和「知道但被拦住」对用户是两种体感，值得点一句。

**「出问题了怎么办」必须区分两种失败**，它们的下一步动作完全不同：

| 你看到的                            | 真实原因         | 该做什么               |
| ----------------------------------- | ---------------- | ---------------------- |
| 提示去 `chrome://extensions` 开开关 | 浏览器权限还没给 | 照着开，然后重试       |
| 提示文件打不开，可能已被移动或删除  | 文件真的不在了   | **不用再去动那个开关** |
| 提示这个格式读不了                  | 类型不在四类之内 | 转成 pdf 或文本再试    |
| 提示当前模型看不了图片              | 模型没有识图能力 | 换个模型（第 12 章）   |

**第二行是重点**：文件没了的时候**不要再让读者去折腾权限开关**——
这是最常见的误导，会让人白忙一场还以为是产品坏了。
