# 第五部分 · 场景实战（第 24-30 章）

**不引入任何新功能**，只把前面的能力组合成完整任务。
**第 5 轮写**——必须等前面章节都写完，因为本部分大量交叉引用。

> **本部分从 5 章扩到 7 章。**
> 新增第 28 章（说一句话替你填表）和第 29 章（把文档内容录进系统），
> 原第 28 章扩写为第 30 章（技能的一生）。
> 原因：前 4 章全是「它给我看什么」，
> **缺了「它替我做什么」——而后者才是用户感知最强烈的能力。**
> 第六部分相应顺延为第 31-33 章。

---

## 0. 本部分的通用规则

### 0.1 必须用 Demo 的真实快捷提示

Demo 的 `src/demo/webskill/quickPrompts.ts` 里有现成的高质量提示词，
中英文都有。**直接用它们**，不要自己编——编的提示词可能跑不出预期结果。

中文文档用中文提示词，英文文档用英文提示词，不要机翻。

### 0.2 每章的固定结构

模板见 [../01-architecture/03-page-templates.md](../01-architecture/03-page-templates.md) §2：
开始之前 → 第一步/第二步/… → 换个说法也能做到 → 这一步用到了什么 → 出问题了怎么办。

「**换个说法也能做到**」是本部分的特色小节：给 2-3 个不同措辞，
证明助手不依赖固定咒语。这一节能显著降低读者的使用门槛。

「**这一步用到了什么**」是导流枢纽，用表格把本章每个环节映射回前面的章节。

### 0.3 截图必须来自同一次运行

一章内的截图要来自**同一次连贯运行**，否则数据对不上，读者会发现破绽。
拍摄方法见 [../03-visuals/04-capture-runbook.md](../03-visuals/04-capture-runbook.md) §10。

### 0.4 诚实标注

每章第一张结果截图下方必须有：
`示例运行结果，你的实际输出会有所不同。`

### 0.5 「它替你动手」类场景的额外规则（第 28、29 章）

前四章是**助手给你看东西**，第 28、29 章是**助手替你改东西**，
读者的心理门槛完全不同。这两章额外遵守：

1. **每写一条"它能做什么"，紧跟一条"你在哪儿还捏着控制权"。**
   不允许出现只讲能力、不讲刹车的段落。
2. **提交前的确认卡必须出现在截图里**，而且要和"已填好的表单"
   在同一次连续运行中拍到。
3. **不能拿跑不通的流程凑数。** 步骤写进书之前必须实际跑通；
   跑不通就换素材或降级写法，**不要编**。
4. **失败路径要写**：拒绝之后会怎样、填错了怎么改。
   只写顺利路径的动手教程会让读者第一次遇挫就弃用。

## 第 24 章 · 生成一份敏捷运营报告 `case-report`

### 目标

读者能用一句话让助手产出覆盖多个数据面的结构化报告，并看懂它是怎么做到的。

### 用到的 Demo 素材

| 项           | 值                                                                       |
| ------------ | ------------------------------------------------------------------------ |
| 提示词（中） | `生成当前项目的敏捷运营报告，覆盖迭代健康、需求分布、缺陷热点和测试质量` |
| 技能         | `agile-ops-dashboard` / `sprint-progress-report`                         |
| 页面工具     | `list_requirements`、`list_sprints`、`list_bugs`、`list_test_suites`     |

### 内容要点

- **本章的教学重点是"多次取数"**：一句话背后，助手调用了多个工具分别取需求、
  迭代、缺陷、测试数据，再汇总。运行步进里能清楚看到这个过程。
  这是理解「助手不是在编，是在查」的最佳案例。
- 第二步「看助手怎么干」要展开运行步进，逐条对照工具名与它取的数据。
- 结尾链接第 11 章（看懂运行）与第 16 章（下载产物）。

### 图

- **M-25 一句话背后发生了什么**（sequenceDiagram）：
  参与者 `你` / `助手` / `页面工具` / `技能`，
  展示多次取数与最终汇总。**用户语言命名参与者**，不要用组件名。

### 截图

| 编号             | 内容                               |
| ---------------- | ---------------------------------- |
| S-case-report-01 | 提问时刻（快捷提示或输入框）       |
| S-case-report-02 | 运行步进展开，能看到多次工具调用   |
| S-case-report-03 | 单次工具调用详情（取到了什么数据） |
| S-case-report-04 | 最终报告                           |
| S-case-report-05 | 下载产物                           |

### 判据

- 运行步进的截图里能数出多次工具调用。
- 「换个说法」给了至少 2 个变体且都验证过。
- 交叉引用表覆盖至少 4 章。

## 第 25 章 · 让助手总结我正在看的页面 `case-summarize`

### 目标

读者学会不复制粘贴、直接让助手读当前页面并总结。

### 用到的 Demo 素材

| 项           | 值                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 提示词（中） | `读取我当前正在看的这个页面的内容，总结出关键信息和异常项`                                                       |
| 变体         | `给我当前页面的速览总结：我在哪个屏幕、正看哪个项目，以及它的需求池规模、迭代进度、未关闭缺陷和测试质量头条数据` |
| 屏幕         | 在 Demo 的不同屏（需求/迭代/缺陷/测试）各试一次                                                                  |

### 内容要点

- **本章的教学重点是"同一句话在不同页面得到不同结果"**：
  在需求屏问和在缺陷屏问，助手总结的东西不一样。
  这最能说明"它真的读了你在看的页面"。**做成对比截图。**
- 结合第 13 章：展示感知提示条（正在读取页面内容，区域：…）。
- 进阶变体：读带附件的需求文档并抽取验收标准
  （提示词见 quickPrompts，涉及 `requirement-doc-digest` 技能）。

### 图

本章**不需要新图**，引用第 13 章的 M-14 即可。
（提醒：能用一句话说清的不要画图。）

### 截图

| 编号          | 内容                          | 要点                           |
| ------------- | ----------------------------- | ------------------------------ |
| S-case-sum-01 | 在需求屏提问 + 结果           |                                |
| S-case-sum-02 | 在缺陷屏用同一句话提问 + 结果 | **与 01 构成对比**，本章最重要 |
| S-case-sum-03 | 感知提示条                    |                                |
| S-case-sum-04 | 带附件需求的文档抽取结果      | 进阶变体                       |

### 判据

- 有同一提示词在两个不同屏的对比截图。
- 明确写出「它读的是你当前这一屏」。
- 链接第 13 章说明读取边界（密码框不读等）。

## 第 26 章 · 出一份可打印的质量通报 `case-bulletin`

### 目标

读者能产出一份格式规范、可直接打印或存 PDF 的公文。

### 用到的 Demo 素材

| 项           | 值                                                                               |
| ------------ | -------------------------------------------------------------------------------- |
| 提示词（中） | `为当前项目生成一份可打印的质量通报公文，包含缺陷趋势、测试覆盖和发布就绪度结论` |
| 技能         | `quality-bulletin` / `authored-bulletin`                                         |

### 内容要点

- **教学重点是"产物是有版式的"**：不是一段纯文字，而是排好版、能直接打印的公文。
- 打印步骤要写全：打开文档 → 浏览器打印 → 存为 PDF，
  并说明**技能设定的版式（页边距等）会被保留**（依据 `documentSurface.spec.ts`）。
- 与第 16 章呼应，第 16 章讲能力，这里讲完整流程。

**★ 本章必须演示「改一版」**（对应第 7 章「现成的 / 现做的」）：

上面那句笼统的提示词走的是固定模板（`quality-bulletin`），**版式一个字都改不了**。
所以本章要在拿到第一版之后，**再追加一句修改要求**，例如：

```
只保留这个迭代的数据，把发布就绪度那段换成一个表格
```

读者会看到：助手**重新出了一版**（改用 `authored-bulletin` 现场撰写），
而不是在原件上微调。**这一步必须写明白**，否则读者会以为它没听懂自己的话。

同时给出更省事的做法：**一开始就把要求说清楚**，可以少跑一轮。

```
为当前迭代生成一份质量通报公文，只要缺陷趋势和测试覆盖两部分，结论用表格
```

### 图

- **M-26 从一句话到一份 PDF**（flowchart）：
  `提出需求 → 助手生成公文 → 在对话里预览 → 打开文档 → 打印/存 PDF`。
  **末端加一条回流边**：`提出修改 → 重新生成一版`，回到「助手生成公文」节点。

### 截图

| 编号          | 内容                               |
| ------------- | ---------------------------------- | ------------------------------ |
| S-case-bul-01 | 对话里的公文预览                   |
| S-case-bul-02 | 打开文档后的完整版式               |
| S-case-bul-03 | 浏览器打印预览（版式保留）         |
| S-case-bul-04 | 导出的 PDF                         |
| S-case-bul-05 | **提出修改要求后重新生成的第二版** | ★ 与 01 并排对比，技能标记不同 |

### 判据

- 打印流程步骤完整可复现。
- 有打印预览截图证明版式保留。
- **演示了「提修改 → 重做一版」，并说明了这是换用了另一个技能，不是原地改。**

## 第 27 章 · 做一套幻灯片并放映 `case-slides`

### 目标

读者能让助手做出可放映、可翻页、可导出 PDF 的幻灯片。

### 用到的 Demo 素材

| 项           | 值                                                                       |
| ------------ | ------------------------------------------------------------------------ |
| 提示词（中） | `把所有项目的交付质量做成一份幻灯片，在新窗口里放映，支持翻页和导出 PDF` |
| 技能         | `agile-slide-deck` / `authored-slides`                                   |
| 投放面       | 站点的 `viewer.html`                                                     |

### 内容要点

- **必须写开窗授权**：新窗口放映前会有确认卡，
  **你不同意就不会开窗**（依据 AC-13.4 / 13.14）。这是安全叙事的一部分。
- 放映操作：翻页、全屏、退出。
- 导出 PDF：并说明**深色幻灯片打印时不会丢底色**（依据 `documentSurface.spec.ts`）。
- 这是全书视觉效果最好的一章，截图质量要高。

**★ 幻灯片这里的「现成 / 现做」差别最明显，必须讲**：

固定模板（`agile-slide-deck`）**页数、页序、内容全部写死**——就是八页，
讲的是三个演示项目的综合分析。你想加一页、少一页、换个讲法，它都做不到。

现做的（`authored-slides`）**页数由内容决定**，你可以指定讲什么、分几页、
做完还能要求加减页。给一组对照例子：

```
「把所有项目的交付质量做成一份幻灯片」        → 固定八页，最快
「就讲当前迭代，分三页：进展、风险、下一步」  → 现做的，按你说的分页
「幻灯片做好了，在风险后面加一页缺陷明细」    → 现做的，重做一版
```

**这是全书解释"为什么有时候页数不一样"的地方**，读者遇到过就会来查。

### 图

- **M-27 幻灯片的产生与放映**（flowchart）：
  `需求 → 助手生成幻灯片 → 请求开窗 → 你同意 → 在新窗口放映 → 翻页 / 导出 PDF`。
  「你同意」这一环是必经节点，不能省。
  **同样加一条回流边**：`提出加减页 → 重新生成一版`。

### 截图

| 编号             | 内容                       | 要点                             |
| ---------------- | -------------------------- | -------------------------------- |
| S-case-slides-01 | 开窗确认卡                 | 必须有                           |
| S-case-slides-02 | 放映中的幻灯片（首页）     | 本章封面图                       |
| S-case-slides-03 | 翻到下一页                 | 证明可翻页                       |
| S-case-slides-04 | 导出的 PDF（深色底色保留） |                                  |
| S-case-slides-05 | **按指定分页生成的一版**   | ★ 页数与固定模板不同，与 02 对比 |

### 判据

- 开窗需授权写清楚了并有截图。
- 深色底色保留有证据。
- 拒绝开窗的后果也写了（助手会说明没能打开）。
- **讲清了固定八页与"页数由内容决定"的差别，并有对照例子。**

## 第 28 章 · 说一句话，它替你把表填好 `case-fill-form`

### 目标

读者亲眼看到"我说，它填"，并且**明白提交前一定会停下来问他**。

> **这一章是全书对新读者冲击力最大的一章。**
> 前面所有章节讲的都是"它给我看什么"，这一章第一次讲"它替我做什么"。
> 写作时把重心放在**用户的体感**上：省了多少次敲键盘、
> 以及"我什么时候还捏着控制权"。

### 用到的 Demo 素材

| 项       | 值                                                                         |
| -------- | -------------------------------------------------------------------------- |
| 快捷提示 | 「根据我的想法规划新需求、迭代任务和测试用例，带我到各个页面逐个创建落地」 |
| 屏幕     | 需求池 → 迭代看板 → 测试用例（跨三个屏幕，一路填过去）                     |
| 表单     | 需求表单、迭代任务表单、测试用例表单                                       |
| 输入方式 | **键盘打字 与 语音口述 两种都要演示**                                      |

**这条快捷提示是 Demo 现成的**（`src/demo/webskill/quickPrompts.ts`），
一句话会连着填三个不同页面的表单，比自己编的提示词有说服力得多。

### 内容要点

**第一步要写"用说的"，不是"用打的"。**
本章是第 10 章语音输入的最佳落地场景：**按住说一句话，它就开始填表**。
这是读者能立刻感知到的价值——不用打字、不用切页面、不用记字段。

要走通的完整链路：

1. **你说出想法**（语音，或者打字）。
2. **它带你到该去的页面**（第 13 章的屏幕跳转）。
3. **它把字段一个个填好**——这里要明确写：**这一步不会打断你**。
4. **到"提交"时它停下来问你**——弹确认卡，你看一眼再点允许。
5. **提交成功，页面上真的多了一条**。

**第 3、4 步的对比是本章的灵魂**，必须写成显眼的一句话：

> 它可以自己把整张表填满，但**按下"提交"之前一定会停下来问你**。

规则出处见第 14 章「哪些事它会先问你」，本章不重复解释，只给链接。

**★「它凭什么知道该填什么」——本章必须回答。**
读者看到一张表凭空被填满，第一反应往往不是惊喜，而是警觉：**这些值它从哪弄来的？**
不主动回答，读者就会自己假设最坏的那种。来源分三档，必须分开写：

1. **你刚才那句话里就有的。** 标题、优先级这些你亲口说了的，它直接用。这一档不用解释。
2. **你没说、但它记得你的习惯。** 比如指派给谁、估几个点。
   这类字段它**不会直接替你填**，而是在旁边摆一个**建议值**，
   并附一条**建议依据**——「你最近几次都指给了这个人」。
   **你点了采纳才算数**，不点就还是空的（机制见第 8 章）。
3. **前两样都没有。** 字段**留空**。它不会编一个看起来合理的值糊弄过去。

第 2 档是「用得越久越顺手」的全部来源，要用一句大白话交代它从哪学的：
**从你以前怎么回答、怎么选择里学的，学到的东西存在你自己的机器上，
可以逐条查看、逐条删除**（第 23 章讲怎么管，第 33 章讲它会不会外发）。

**第 3 档不能省。** 只写第 2 档，读者会以为它什么字段都敢猜；
把「猜不出来就空着」一起写出来，第 2 档的建议才显得可信。
这也顺带解释了新读者的困惑——**头几次用的时候一条建议都不会有，因为它还不认识你**。

**必须写的三件事**：

- **填错了怎么办**：字段是填在页面上的，**你可以直接改**，
  改完再点允许提交。不需要让助手重来。
- **不想让它提交**：点「拒绝」，这一条就不会写进去，
  但助手会继续做后面的事（比如接着填下一张表）。
- **不想每次都问**：确认卡上可以勾「不再询问」，
  但要提醒——**这等于把提交权交出去了**，
  撤销的地方在第 23 章。这一句不能省，属于诚实告知。

**「换个说法也能做到」**（本章至少给三条，证明不用背咒语）：

- 「帮我把这个需求建到需求池里，标题叫……，优先级高」
- 「我要加一个迭代任务：……，估 3 点，指给我」
- 口述版：直接按住语音键把上面的话说出来

**形态差异**：网页版和扩展版在本章**行为一致**，
差别只在语音——扩展版的麦克风**需要先在普通标签页里授权一次**（第 10 章）。

### 图

- **M-28 一句话变成一条记录**（flowchart）：
  `你说一句话 → 它读懂 → 跳到对应页面 → 逐个字段填写（不打断你）→
【停】提交确认卡 → 你允许 → 写入成功`。
  **「【停】」那一格要在视觉上突出**（加粗框或不同颜色），
  它是这张图存在的理由。
  再从「你允许」引一条虚线到「也可以拒绝 → 这条不写入，但任务继续」。

否则读者会怀疑是拼出来的。拍法见
[../03-visuals/04-capture-runbook.md](../03-visuals/04-capture-runbook.md) §10。

S-case-form-07 要能同时看清**建议值**和**那条依据**；
依据被截掉的图不算数——本章引用它就是为了证明「它会告诉你凭什么这么猜」。
画像为空时拍不出这张图，需要先正常用一段时间（见第 8 章 S-interactions-09 的攒法）。

### 判据

- **演示了语音口述这条路径，不是只有打字。**
- **「填写不打断、提交要确认」这条规则在本章被明确说出，并有连续两帧截图佐证。**
- **回答了「它凭什么知道该填什么」，三档来源齐全，「猜不出来就留空」没有被省掉。**
- 写明了填错可以手动改、拒绝之后任务会继续。
- 「不再询问」的代价被诚实告知，并给了撤销路径。
- 至少三条不同说法，证明不依赖固定措辞。

## 第 29 章 · 把一份文档里的内容录进系统 `case-import-file`

### 目标

读者学会**把已有的文件交给助手，让它替自己录入**，
并且知道文件在这个过程里去了哪。

> 这是第 28 章的进阶：上一章的信息来自你的嘴，这一章来自一份文件。
> 对每天要把 Excel / Word 里的东西手工敲进系统的人，
> **这一章就是整个产品的卖点。**

### 用到的 Demo 素材

| 项       | 值                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------ |
| 快捷提示 | 「读取我当前正在看的需求列表里带附件的那几条需求文档，抽出验收标准，并列出文档里有、需求单里缺的条目」 |
| 素材文件 | `public/demo/attachment/` 下的 `.docx`（中英文各若干，**Demo 自带**）                                  |
| 屏幕     | 需求池 → 需求详情 → 需求表单                                                                           |

**关于 Excel**：附件类型里 `xlsx` 是支持的（第 10 章），
但 **Demo 自带的素材只有 `.docx`，没有 `.xlsx`**。
写这一章时**二选一，不要含糊**：

- 用 Demo 自带的 `.docx` 走通全流程（**推荐**，可复现、截图可信）；
- 或自备一个 `.xlsx` 实拍，但必须**实际跑通再写**，
  并在图注里说明这份文件是自备的。

**严禁**凭"格式支持"就编一段 Excel 流程截图——跑不通的步骤会毁掉整本书的可信度。

### 内容要点

**开篇先讲清一件事：这份文件去哪了。**

Word / Excel 这类文档，**是在你自己的浏览器里被抽成文字的**，
发给模型的是抽出来的文字，**不是原文件**。
这一条既是能力说明，也是隐私说明，**必须写在最前面**，
并链接到第 33 章。读者在上传公司文档前最想知道的就是这个。

**完整链路**：

1. **把文件拖进输入框**（或点回形针选）。
2. **附件小片上显示类型**——文档类会标成「文档正文」。
3. **说一句你要它干什么**（"把这份文档里的验收标准录成需求"）。
4. **它读出内容，告诉你它准备录什么**——这一步很重要，
   要提醒读者**在这儿核对一遍**，比录完再改省事。
5. **它去填表**（同第 28 章：填写不打断、提交要确认）。
6. **逐条录入**——多条内容会变成一个任务清单，
   你能看到"第 3 条 / 共 7 条"这样的进度（第 11 章）。

**必须写的边界**：

- **文本太长会被截断**（上限 32 KB，见第 10 章）。
  大文件要提醒读者：**分段传，或者先说清只要哪一部分**。
- **抽出来的不一定全对**——表格复杂、格式花哨的文档抽取质量会下降。
  给出可操作的建议：**先看第 4 步它复述的内容，再让它动手**。
- 一次录多条时，**中间某条被你拒绝，不影响后面的**（第 14 章）。

**「换个说法也能做到」**：

- 「照这份文档，把里面列的需求建到需求池」
- 「这个文件里的验收标准，逐条加到当前需求上」
- 「先别录，你先说说你从这份文档里读到了什么」（★ 推荐给谨慎的读者）

### 图

- **M-29 一份文件变成系统里的记录**（flowchart）：
  `选文件 → 【在你的电脑里】抽成文字 → 文字发给助手 → 它复述准备录什么 →
你确认 → 逐条填表 → 每条提交前确认 → 录入完成`。
  **「【在你的电脑里】」那一格要标注清楚**，
  并在图注写明"原文件没有整份发出去"——这是本图最重要的信息。

| ---------------- | ---------------------------------------------- |
| S-case-import-01 | 把 docx 拖进输入框，小片显示「文档正文」       |
| S-case-import-02 | 助手复述它从文档里读到的内容（录入前的核对点） |

### 判据

- **开篇就写明文档是在本地抽成文字的，原文件不会整份发出去**（链接第 33 章）。
- **用的是真跑通的文件类型**；若用自备 xlsx，图注里标注了。
- 写明了 32 KB 截断这条边界，并给出应对办法。
- 提醒读者在"它复述内容"这一步核对。
- 多条录入的进度可见，且写明单条拒绝不影响其余。

## 第 30 章 · 把这次做过的事变成一个技能 `case-skill-lifecycle`

### 目标

读者走通技能的**完整一生**：从一次对话沉淀出来 → 审批 → 生效 →
改进 → 不满意回滚。

> **本章由原「让助手改一个技能」扩写而成。**
> 原章只讲了"改"，**缺了最前面的"从哪来"**——
> 而"把刚做过的事存下来"恰恰是 Demo 的卖点之一
> （`src/demo/webskill/runtime.ts` 原话）。补上之后，本章才是完整闭环。

### 用到的 Demo 素材

| 项         | 值                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------ |
| 快捷提示   | 「先列出当前项目的缺陷清单，再读取本项目的 DORA 指标，然后把「查缺陷、读指标」这个流程固化成一个技能」 |
| 技能       | 上面那条提示词现场生成的技能；改动演示可用 `sprint-weekly-brief`                                       |
| 控制台页面 | 技能库 → 编辑器 → 审批队列 → 版本                                                                      |

**那条快捷提示是 Demo 现成的**，一句话就把"做事 → 沉淀成技能"演完，
是本章最好的开场。

### 内容要点

#### 第一段：从一次对话里长出一个技能（★ 新增，本章新的开头）

用户视角一句话：**你带着助手把一件事做成了，可以把这个过程存下来，
下次一句话重跑。**

要写清四件事（详见第 7 章，本章是完整演一遍）：

1. **它会先给你看**。确认文案要原文引用：
   「将本次对话保存为技能「{name}」？…**请逐字检查下方预览，
   确认没有不应被保存的内容。**」
2. **请你真的检查一遍**。对话里可能有不该沉淀的东西——
   具体的人名、内部数字、一次性的口令。
   **这句提示要写成读者的责任，不能弱化。**
3. **存下来不等于能用**。它进的是审批队列
   （「「{name}」已提交待审。审批并发布后才能使用。」），
   审过、发布了才生效。**不写清楚，读者会以为存完就能调**。
4. **可以直接跳过去看**。提交后给候选 ID，可复制，
   也能点「去审批」直接到控制台（第 21 章）。

**一个要提醒的坑**：如果这轮任务里有步骤被**委派**给了别的技能，
可能会存不成（第 11 章有解释）。给出做法：
不带委派把关键步骤重做一次，再存。

> **形态提醒**：这个能力有开关（控制台 → 智能体运行时 → 技能自动生成）。
> Demo 默认开着，**别的系统可能关着**，要写一句"如果你没看到这个入口……"。

#### 第二段：改一个技能（原有内容）

- **这是全书唯一允许展示文件内容的章节**（技能文件本身）。
  即便如此，展示的也是技能的**说明与模板文本**，不是 SDK 代码。
- 两条路径都要写：
  1. **你自己在编辑器里改**——直接编辑、保存即校验。
  2. **让助手改**——助手生成的改动会进入审批队列，等你确认。
- 强调安全叙事：**改动不会不打招呼就生效**，要经过你审查（第 21 章）。
- 改坏了可以回滚（第 21 章版本页），给出退路。

### 图

- **M-30 一个技能的一生**（flowchart）：
  `一次成功的对话 →（你说"存成技能"）→ 预览确认 → 进审批队列 →
审批通过并发布 → 可以调用了 → 用起来发现要改 → 改动（你改 / 它改）→
再次审批 → 生效 → 不满意 → 回滚到上一版`，
  末尾画一条**回流边**指回"可以调用了"，体现这是个循环。
  **这张图取代原 M-28**，把第 7、19、21 章全串起来。

**两张都不能省**。

### 判据

- **「从对话沉淀技能」写全了四件事：先给你看、请你检查、要审批才能用、可跳转。**
- **"请逐字检查预览"的责任提示被原样传达，没有弱化。**
- **写明了存下来不等于立刻可用。**
- 提到了"步骤被委派可能存不成"这个坑，并给了做法。
- 两条改动路径都写了；「改动要经你确认才生效」明确写出。
- 有回滚退路。
- 前后两段各有闭环验证截图（S-case-life-05、S-case-life-07）。

| **让它自查一致性** | 「检查当前项目的需求状态和迭代阶段是否自洽，把不一致的列出来」                                         | 纯只读、零风险，适合给不敢授权的读者当第一个"动手"体验             |
| **迭代收尾核对**   | 「对当前迭代做收尾核对，覆盖假完成需求、未关闭缺陷分级和测试覆盖缺口，给出结转清单与下迭代建议」       | 一次跑完多个数据源，是展示任务清单（第 11 章）的最佳素材           |

**挑选原则**（按重要性排序）：

1. **用户在场景里是"甩手掌柜"而不只是"观众"**——
   参见 [../05-quality/03-pitfalls.md](../05-quality/03-pitfalls.md) 陷阱 22。
2. **有 Demo 现成的提示词**，跑得通、可复现。
3. **能顺带演示一个前面章节讲过的机制**（列表逐项、任务清单、图片理解…），

4. **风险梯度要有高有低**：像"自查一致性"这种纯只读的场景，

## 附 · 「它越用越懂你」类场景（备选，演示条件特殊）

上面那批场景**开箱即可复现**：装好 Demo，点快捷提示词就能跑。
下面这批不一样——它们的效果**依赖你先用过一段时间**，
因为要演示的正是「它记住了你的习惯」。这类场景单独列，
是为了防止写作者把它们混进上表，然后发现照着步骤跑不出截图。

| 候选场景                   | 用户说的话                     | 它多做对了什么                                                                 |
| -------------------------- | ------------------------------ | ------------------------------------------------------------------------------ |
| **建单时替你想起指派人**   | 「建一条需求：登录页加验证码」 | 你没提指派给谁，它建议了你最近几次都选的那个人，并写明「你最近几次都指给了他」 |
| **「照老规矩来」**         | 「照老规矩再建一条」           | 「老规矩」是你以前明确说过的偏好，它据此把优先级、模块、估点一次配齐           |
| **报告按你关心的口径出**   | 「出一份这周的进展报告」       | 你以前说过「我只看 P0」，它就按这个口径出，而不是把所有优先级堆给你            |
| **表单里那几个你从不改的** | 任何一次建单                   | 估点、所属模块这类你每次都填一样的字段，它直接给出建议值，你点采纳就行         |
| **换了项目之后主动纠偏**   | —                              | **反例场景**：老建议在新项目里不适用了，教读者去把那几条删掉                   |

**这五个场景合起来才完整**，尤其最后一个不能省：
前四个讲「它猜得准真省事」，最后一个讲「猜得不准时你能把它掰回来」。
只写前四个，这一族场景就变成了没有刹车的能力吹嘘——
违反 §0.5 定下的「能力必配刹车」。

**写这一族场景的三条硬规矩**：

1. **不许摆拍建议值。** 建议那一行必须是真攒出来的。
   做不到就不要写这个场景，**绝不允许 P 一张建议上去**——
   全书的可信度建立在"截图都是真跑出来的"这个前提上，破一次就全塌了。
2. **必须写清楚「你得先用一阵子」。** 否则读者照着做、发现没有建议，
   会认为文档在骗人。把「新用户看不到建议是正常的」放在这一族场景的开头。
3. **每个场景都要带上"怎么关掉/怎么删"。** 指向第 23 章。
   讲「它记得你」而不讲「你能让它忘掉」，读者的感受是被监视，不是被服务。

**素材提醒**：Demo 里画像是**默认开着**的
（`src/demo/webskill/runtime.ts` 注释：「个性化画像（T6）也是演示主线之一，
`userProfile.enabled` 缺省打开」），所以这些场景在 Demo 上能跑通。
但 SDK 的**出厂默认是关闭**的（`verify/agent/13-privacy-profile.md` A-94），
写「网页版与扩展版的差别」时不要把 Demo 的设定当成产品的设定——
这是本书第二处「Demo 开、出厂关」的对子，第一处是技能自动生成（第 7 章）。
